# 05. 采集、Spool 与投递可靠性

## 5.1 Client 启动顺序

Client 先严格解析当前配置，验证 state directory，取得单实例锁，读取或建立 Host identity，恢复配对与
spool，再初始化采集器和投递器。只有长期运行所需组件都就绪后才报告 service ready。

## 5.2 快速与慢速采样

CPU、内存等可按基础周期采集；设备枚举、GPU 或传感器等昂贵项可按慢周期缓存。周期加入有界 jitter，
避免大量客户端整点同时请求。jitter 不能把最小/最大周期推到配置边界之外。

## 5.3 Spool 的角色

spool 是磁盘上的有界待投递队列，不是无限历史库。报告在发网前落盘，成功确认后删除；崩溃或暂时网络
错误后可重放同一 report ID。目录及文件必须是受保护普通对象，拒绝链接和宽权限替换。

## 5.4 容量压力

持续离线最终会填满 spool。系统必须有明确的最大字节、条目和单报告边界，并暴露状态；不能无限增长
耗尽主机磁盘。达到上限时的舍弃/拒绝策略要由当前实现和测试决定，不能在异常路径静默改变。

## 5.5 投递轮次

投递器按文件名 FIFO 从 spool 每次取一条，每轮最多连续处理 32 条；HTTP report API 本身不是多报告
batch。使用绑定了 Client identity 的 credential 快照与 HTTPS；只有 debug 构建允许 loopback HTTP，
正式构建不接受该策略，也没有持久配置开关可启用远程明文 report/OTLP。连接失败、429、503 等可重试
结果保留队首并施加退避；严格合同确认的永久内容拒绝才丢当前报告，严格 401 才进入重新授权。

报告身份与当前快照不匹配时，在联网前拒绝，由 Foundation 将原容器无覆盖地隔离为 `.identity`，
然后继续处理本轮其他记录；隔离也计入每轮 32 条投递项上限。它不是 ACK，不发送 OTLP、不使新凭据
失效，也不重写旧报告的 Host ID。若目标冲突或磁盘操作失败，则保留原记录和已有证据，停止本轮。

`status --output json` 的 `spool_identity_mismatch_batches` 是身份错配隔离数量，
`spool_invalid_batches` 包含全部隔离项。`status` 和只读 `doctor` 用 `spool_identity_mismatch` 提示
这类问题，且不修改状态或回显载荷。这是有界清单检查，不等于验证了所有内容。隔离文件重启后保留，
仍占用容量；请先核对配对和证据归属，不要改名后用当前实例凭据重放，也不要期待自动清空证据。

## 5.6 优雅停机

收到停止信号后停止新采集，等待已拥有的本地写入和有限网络工作，在 deadline 内同步状态并释放锁。
不能为了“清空所有历史”无限阻塞系统关机，也不能在落盘进行一半时直接退出。

## 5.7 配置与状态分离

配置描述 Server、周期、TLS 和容量；状态描述生成的 Host identity、当前 binding、pending pairing 和
spool。配置管理系统可以部署配置，但不能复制一台机器的状态到另一台，否则会产生身份克隆。

## 5.8 可选 OTLP

OTLP 是编译期可选 feature，默认 Client 不包含它。启用后使用独立 Token 和目标，不能复用设备
credential，也不能把第三方错误正文原样写日志。只有 xsos `202` 已确认且 spool 已删除后，
报告才以 best-effort 方式进入 128 容量 OTLP queue；queue 满、Collector 失败或 Client 停机都允许漏导，
不会恢复 spool 或改变主通路结果。该次序避免重复 OTLP，但明确牺牲次要通路的完整性。

## 5.9 故障场景推演

| 故障点 | 期望结果 |
|---|---|
| 采集器部分失败 | 报告表达缺失/受限错误，不伪造零值 |
| 本地落盘失败 | 不发送无法恢复所有权的报告 |
| 请求发送后断线 | 保留相同 ID，Server 幂等/冲突规则裁决 |
| Server 429 | 退避，spool 继续有界 |
| credential 撤销 | 停止无意义风暴，提示重新配对 |
| 进程崩溃 | 下次在锁与严格状态校验后恢复 |

## 5.10 修改可靠性代码

任何队列修改都要覆盖：满容量、部分文件、重复 ID、重启恢复、权限、磁盘满、请求取消、Server 已提交
但响应丢失、关机 deadline。Happy path 单元测试不足以证明可靠性。
